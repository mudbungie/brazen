blocked behind a split.

## Evidence

Hit live while closing bl-f90e (c8f01dd): a five-line explanatory comment took the file
to 303 and the gate refused:

    linecount: src/protocol/openai_responses/encode.rs is 303 lines (> 300-line cap for code files)

That was resolved by trimming the comment to fit — a stopgap, not a fix. `wc -l` on
main is now exactly 300.

## The bar

Per the owner rule, 300 is RUNAWAY PREVENTION, not the target; ~200 is the thickness
indicator. Split on a GENUINE seam, never a fake one — do not carve off an arbitrary
100 lines to buy headroom, and do not manufacture a module boundary that leaves callers
reaching across it.

Candidate seams to evaluate (evaluate, not assume — pick what the code actually wants):
the request-body assembly vs. the `input[]` item construction (messages, reasoning
replay items, tool results), which is where the file already has its densest logic;
compare against how the sibling dialects are laid out — `src/protocol/anthropic/encode/`
and `src/protocol/openai/encode/` are already directories with a `mod.rs`, and
`anthropic/encode/count.rs` shows the established pattern for peeling a coherent piece
off. That asymmetry is itself the argument: this dialect never got the same treatment.

Behavior must not change — this is a pure move. The gate is the proof: `make check`
green (fmt, clippy, the cap, 100% coverage) with no test edits beyond import paths. If
a split forces a test rewrite, the seam is wrong.
