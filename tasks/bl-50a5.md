Two facts per provider row, as columns beside `name/protocol/auth/credential` (`src/run/providers.rs`):

- **effort** — the row's protocol projects the canonical `reasoning` knob AND the row does not list `reasoning` in `unsupported_body_keys`. Today every dialect projects something (openai `reasoning_effort`, responses `reasoning.effort`, anthropic `thinking.budget_tokens`, google `thinkingConfig`, ollama `think`, claude_code `--effort`), so the interesting bit is the per-row decline.
- **priority** — the row's protocol has a service-tier spelling (openai_chat, openai_responses, anthropic_messages once the service_tier knob lands — see that ball) and no `unsupported_body_keys` decline.

Why here: yog gates seat controls on these facts and today derives them locally as a total match over `ProtocolId` (`yog src/config_edit/brazen/providers/capability.rs`) with the standing migration note "when brazen serves the column, the match is deleted and the column read in its place" — the same note bl-5053 carries for tools/multi-turn. This ball is that upstream ask for the tuning pair. NOT on the critical path of the seat feature (yog's local derivation ships first); landing it deletes downstream code.
