Evidence: the lernie-usability round-2 comparator drove one litany agent through four steps on two provider rows. claude-sonnet-4-6 via claude-session-direct: cache_read 0 / 11342 / 12666 / 13372. gpt-5.5 via openai-chatgpt (Responses, store:false): cache_read 0 / 3584 / 0 / 0. litany's assembly was byte-identical and append-only on both rows (litany bl-b902 measures it in src/prompt/tests/prefix_ladder.rs). The Anthropic encoder places cache_control automatically (src/protocol/anthropic/encode/cache.rs: last system block + rolling mark + one lookback mark) and the claude bill shows it working. The OpenAI Chat and Responses encoders send no prompt_cache_key (repo-wide grep: zero hits) and no previous_response_id (specs/providers.md: brazen is stateless). OpenAI's automatic prefix cache routes by prompt_cache_key; without it a growing, stateless, fully-resent input lands on whichever replica takes it, which is the shape of the 0s. Ask: one canonical field — CanonicalRequest.cache_key: Option<String> — projected to prompt_cache_key by the openai-chat and openai_responses encoders and ignored by the Anthropic encoder (whose placement stays policy, specs/anthropic-messages.md §2.10). Nothing else changes; a None keeps today's wire byte for byte. litany's half (filed as the litany side of bl-b902) is to hand the agent id — one per branch, stable for the branch's life — through that field from src/prompt/dispatch/canonical.rs::build_request once the version that carries it is pinned.

---

Landed as specified, and the WIRE half is proven: a local capture of the encoded body shows prompt_cache_key present verbatim on the openai_responses body, before the extra fold, and absent when the field is None.

The RESPONSE half could not be reproduced on this box, and the reason is not the key. On the only OpenAI route available here (the ChatGPT/Codex backend, openai_responses, store:false forced) a BYTE-IDENTICAL request sent twice back to back reads cache_read 0 on both -- the strongest possible cache case, and it is a miss. Measured over a dozen live calls with a ~9.6k-token stable prefix: with a plain string key, with a UUID key, with and without a reasoning effort, on two model slugs, and with the codex session_id / OpenAI-Beta headers added. Every one read 0, and the raw body confirms the backend itself reports cached_tokens 0 and cache_write_tokens 0 per item -- not a decode gap. store:true is refused by that backend, so the one remaining variable cannot be tested.

So the round-2 comparator's 3584 on gpt step 2 is a hit this route no longer serves, and the absent key was not the whole cause. The lift is still right and costs nothing (None keeps the wire byte for byte, and the key is what the documented API routes by), but "send cache_key and the OpenAI cache warms" is UNPROVEN on the Codex backend today. Worth a separate ball if gpt-side cache spend matters: why that route serves no cache reads at all is a provider-account question, not a brazen one.
