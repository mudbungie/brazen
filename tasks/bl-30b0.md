Surfaced when bl-365f renamed the local row `codex` -> `openai-chatgpt`, making
`BRAZEN_LIVE=1 BRAZEN_LIVE_FUZZ_SPEND=1 cargo test --test live_fuzz_openai -- --ignored`
actually RUN for the first time on this machine. Result: 6/8 ok, 2 FAIL — both in the
error-conformance matrix, both exit 0 where 69 was expected.

## Both causes now PROVEN by direct live probe (2026-07-31), not inferred

Probes ran a hand-built body through `bz --config <copy of the live config with the
`body_defaults` line deleted> --provider openai-chatgpt --model gpt-5.4 --json`.

### 1. `missing-store` — NOT drift. The row masks the case. The mandate still holds.

The live row carries `body_defaults = { store = false }`. The test builds its body by
removing `store` from `valid()`, but `fill_absent` folds row `body_defaults` into
`req.extra` (protocol/mod.rs:198, config §4.1), so `store:false` is put BACK before
encode and reaches the wire anyway -> 200.

PROOF — same request, row `body_defaults` deleted:
```
{"type":"error","kind":{"provider":{"status":400}},"message":"Store must be set to false",
 "provider_detail":{"detail":"Store must be set to false"}}
```
So codex still mandates `store:false`. The suite simply cannot express its absence
through a row that fills it. This is EXACTLY the shape of the `stream` case the test
already documents and excludes:

  "`stream` is NOT in this matrix: serve forces stream:true (serve.rs:112, bl-9e3d) so
   this path structurally cannot put stream:false on the wire — codex's stream mandate
   is unverifiable here."

The file's DRIFT POLICY comment claims the opposite and is now FALSE:
  "`missing-instructions` (instructions <- system) and `missing-store` (store rides
   `extra`) both pass their flipped key through to the wire"
`store` rides `extra`, yes — but the ROW writes it there. Fix is a choice, not a
correction: (a) drop the case from the matrix with the same NB `stream` got, or (b) have
the harness suppress the row default for this one case so the mandate stays a live
tripwire. (b) keeps coverage; it needs a way to say "send this body with NO row fill".

### 2. `missing-instructions` — GENUINE codex drift, 400 -> 200.

Nothing refills `instructions`: `encode` omits the key entirely when `system` is None
(openai_responses/encode/input.rs:29, `instructions()` -> `Option<String>`), and the row
has no `body_defaults` for it.

PROOF — `store:false` present, NO `system`, row defaults deleted so nothing could mask it:
```
{"type":"content_stop","index":0}
{"type":"usage","input_tokens":13,"output_tokens":5,…}
{"type":"finish","reason":"stop"}
{"type":"end"}
```
It GENERATED. The backend no longer requires `instructions`.

The test's own drift policy says what to do, and it is the right call:
  "If one starts returning 200, MOVE it to the acceptance set (assert exit 0 + canonical
   grammar), NOT delete it — the suite still guards a silent re-imposition."

## Docs that are now WRONG about the instructions mandate

The `instructions`-is-required fact is asserted in prose in several places; the assertion
change is the small half, these are the rest:
- `tests/live_fuzz_openai.rs` — the DRIFT POLICY block, incl. "Both STILL 400 (re-verified
  live 2026-06-17)"; re-date it to this probe.
- `specs/auth.md` §10.5/§10.7 — records `instructions` as a hard codex precondition.
- `README.md` — "the codex backend's quirks — no `max_output_tokens`, explicit
  `store:false`, required `instructions` — live entirely in its row as data" (~line 490),
  and the fuzz section's "no `instructions` / no `store` / `stream:false` … Each must 400"
  with the quoted `"Instructions are required"` message.
Note `store:false` STAYS true everywhere — only `instructions` changed.
