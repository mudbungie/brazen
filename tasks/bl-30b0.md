Surfaced immediately after bl-365f renamed the local row `codex` -> `openai-chatgpt`, which made `BRAZEN_LIVE=1 BRAZEN_LIVE_FUZZ_SPEND=1 cargo test --test live_fuzz_openai -- --ignored` actually RUN for the first time on this machine. Result: 6/8 ok, 2 FAIL.

```
-- error conformance (near-free 400s) --
  missing-instructions   FAIL: exit 0 (want 69);
  missing-store          FAIL: exit 0 (want 69);
  unsupported-model      ok (status 400; "The gpt-5-codex model is not supported when using Codex with a ChatGPT account.")
-- request-shape acceptance (5 token-costing runs) --
  all 5 ok (exit 0, canonical grammar)
```

Two DIFFERENT root causes, do not fix them the same way:

1. `missing-store` is STRUCTURALLY UNREACHABLE through this row, not drift. The live
   provider row carries `body_defaults = { store = false }` (pinned so a plain prompt
   works, config.md §4.1.1 / auth §10.5). The test builds its body by removing `store`
   from `valid()`, but body_defaults refills it before encode -> the wire body still has
   `store:false` -> 200. This is the exact same shape as the `stream` case the test
   already documents and excludes: "`stream` is NOT in this matrix: serve forces
   stream:true (serve.rs:112, bl-9e3d) so this path structurally cannot put stream:false
   on the wire — codex mandate is unverifiable here." Same reasoning now applies to
   `store`. The tests/live_fuzz_openai.rs DRIFT POLICY comment asserts the opposite —
   "`missing-store` (store rides `extra`) both pass their flipped key through to the
   wire" — that claim is now FALSE for any row with a body_defaults store. Either the
   case moves out of the matrix with the same NB `stream` got, or the harness must
   suppress the row default for that one case.

2. `missing-instructions` has no such masking — nothing in the row refills `instructions`
   — so exit 0 there looks like GENUINE codex drift (400 -> 200): the backend appears to
   no longer require `instructions`. The tests own drift policy says what to do:
   "If one starts returning 200, MOVE it to the acceptance set (assert exit 0 + canonical
   grammar), NOT delete it — the suite still guards a silent re-imposition." Confirm with
   one hand-run before moving it, and re-date the "Both STILL 400 (re-verified live
   2026-06-17)" line plus auth.md §10.7, which still records both as hard preconditions.

Blast radius beyond the test: if `instructions` is genuinely no longer mandatory, the
mandate is documented in specs/auth.md §10.5/§10.7 and README as a codex hard
precondition — those need the same correction, not just the assertion.

Scope: tests/live_fuzz_openai.rs (error matrix + drift comment), specs/auth.md §10.7,
possibly README. Related: bl-365f (the rename that exposed this), bl-3dc4 (loud-SKIP /
release-gate policy — this is precisely the class of silent pass that work forbids).
