Operator ruling 2026-09-29: it's a knob. Default: output tokens and thinking tokens are ENTIRELY SEPARATE counters. Folding thinking into output_tokens (the industry convention: OpenAI completion_tokens/output_tokens and Anthropic output_tokens contain reasoning; Google's candidatesTokenCount does not) makes one variable shadow another and forces awareness of internals on the consumer; the knob exists only because that convention is what most harnesses expect.

Evidence (bl-0aa3 probe): gemini-2.5-flash, --reasoning medium, --max-tokens 400 → wire usageMetadata thoughtsTokenCount 383 + candidatesTokenCount 13; brazen reported output_tokens 12 and no thinking count anywhere.

Design (mirror the input_total_tokens precedent in canonical/event.rs: providers disagree about containment, the decoder knows the shape, so it answers once):
- Usage gains thinking_tokens: Option<u32>, carried where served: Google thoughtsTokenCount; OpenAI chat completion_tokens_details.reasoning_tokens; OpenAI Responses output_tokens_details.reasoning_tokens; Anthropic serves no split → None (unknown, never 0). Ollama: check what it serves.
- output_tokens DEFAULT = answer-only wherever the split is served: Google candidatesTokenCount as-is; OpenAI chat/Responses = served total − reasoning_tokens (a derivation from two served facts, not an invention). Anthropic cannot be separated: output_tokens stays as served (contains thinking) with thinking_tokens None; document that in the field doc and the spec — absent means unknown, not zero.
- The knob folds thinking INTO output_tokens where the split is known (Google: candidates + thoughts; OpenAI: served total unchanged), leaving thinking_tokens still reported. Default off. Spell it the way the other lifted knobs are spelled (config file + env + flag per config.md's precedence ladder); pick a name that says what it does, e.g. usage_fold_thinking. Not a per-row datum: it is the consumer's accounting preference, not a provider fact.
- Serve/ingress masquerades (OpenAI/Anthropic-shaped usage on the way OUT) should emit the industry shape their clients expect regardless of the knob — check specs/ingress.md for where usage is projected and keep that honest.
- Spec homes: canonical-protocol.md §3.2 Usage, architecture.md §3.2 (the usage-accounting section), providers.md §4.6 (Google usage), openai-chat-mapping.md and openai_responses usage rows, anthropic-messages.md usage row, config.md (the knob), README/SKILL.md --json usage example if shown. Tests per decoder for both knob states; the --json projection gains the key (grows-only, skip_serializing_if none).
