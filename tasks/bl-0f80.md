Round 1, lane comparator (lernie suite usability campaign). bz 0.0.14.

Driving hermes-agent 0.15.2 (a Python agent harness on OpenAI SDK 2.24.0)
against `bz --serve`, every request fails before it reaches a provider:

    $ hermes chat -q "Say exactly: HERMES OK"
    Non-retryable error (HTTP 400): HTTP 400: data: {"error":{"code":400,
      "message":"stream_options: Extra inputs are not permitted","param":null,
      "type":"invalid_request_error"}}

Reduced to curl against the ingress:

    curl http://127.0.0.1:PORT/v1/chat/completions -H content-type:application/json \
      -d "{\"model\":\"gpt-4o\",\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}],\"stream\":true,\"stream_options\":{\"include_usage\":true}}"
    {"error":{"code":400,"message":"stream_options: Extra inputs are not permitted",…}}

The same body without `stream_options` succeeds and streams normally, so this
is the only blocker on that path.

Why it matters more than one harness: `stream_options: {"include_usage": true}`
is how the official OpenAI SDK asks for token usage on a streamed completion,
and it is sent UNCONDITIONALLY by the client library, not by the harness author
— hermes` call site is one line with no config knob
(`agent/chat_completion_helpers.py`, the stream kwargs). Any consumer built on
that SDK that streams therefore cannot use `bz --serve` at all, which is
precisely the population `--serve` exists for ("Point an OpenAI-only harness at
ANY provider", specs/ingress.md §"The masquerade").

Proposed shape: `stream_options.include_usage` is not an extra knob to carry —
brazen already emits usage on its own terminal event, and the openai_chat
encoder already knows how to write a usage-bearing final chunk. Decode it as
what it is (a request for the usage chunk the encoder can already produce) and
otherwise ignore the object; an unknown *sub*-key inside it should be dropped,
not refused. That keeps the decoder`s "refuse rather than silently drop" posture
for fields that change meaning, while not refusing a field that only asks for
something the stream already carries.

Second, smaller half: this decode refusal arrives as an in-band SSE `error`
event and `bz --in openai_chat` then exits 0. A request that was never encoded
and never sent upstream is a usage/decode failure (64), not a mid-stream
failure, so the exit code is the wrong one for the one case a script can act on.

Workaround in use by the comparator lane: a ~40-line local proxy that deletes
`stream_options` from the body and forwards to the ingress.
