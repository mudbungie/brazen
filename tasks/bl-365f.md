Found while closing bl-1ad0 (2026-07-30): `tests/live_support/openai.rs` hardcodes
`PROVIDER = "openai-chatgpt"`, but this machine's working credential row is named
`codex` (`~/.local/share/brazen/credentials/codex.json`). Result: with fully valid,
working credentials on the box, `BRAZEN_LIVE=1 BRAZEN_LIVE_FUZZ_SPEND=1 cargo test
--test live_fuzz_openai -- --ignored` SKIPs every case ("no stored `openai-chatgpt`
cred") — while a direct `bz --provider codex --json` call with the same body returns
a live 2xx stream.

This is the exact failure mode the release-gate work (bl-3dc4 / specs/release.md)
names as forbidden: an absent-looking credential silently reading as pass. Here it is
worse — the credential is PRESENT, just under a different row name.

## The contention (not obviously answerable — may need owner ruling)

Two candidate fixes, different owners:
1. Parametrize the test's provider row name (e.g. `BRAZEN_LIVE_OPENAI_CHATGPT_PROVIDER`
   or reuse an existing selection mechanism) so the suite follows the machine's config.
   Cost: a new env knob (smell per AGENTS.md — prefer an existing explicit signal).
2. Rename the local row `codex` → `openai-chatgpt` so machine config matches the
   suite's expectation. Zero code, but it's per-machine ops the repo can't enforce,
   and the row name `codex` is load-bearing in the owner's local workflow/docs
   (memory + auth recipes refer to `--provider codex`).

Either way the SKIP should name the looked-for row so the mismatch is diagnosable at
a glance.

## Scope

`tests/live_support/openai.rs` (and siblings that share the constant), or ops-only
depending on the ruling. Related: bl-3dc4 (loud-SKIP policy), bl-1ad0 (where found).
