Sibling of bl-75f7 (context window on the read surface), filed from bl-68ad.

Today a provider row's inability to carry a request shape surfaces only at encode, at call
time: the `claude_code` protocol rejects tool declarations and multi-turn transcripts with
ParseInput/64 (src/protocol/claude_code/encode.rs, spec claude-code.md §4.1/§4.2). That is
correct per arch §3.1 — but nothing upstream can SEE the decline. Real cost observed in
bl-68ad: yog's model picker validated provider=claude-code for a tool-bearing worker role
(it only checks the row exists in `bz --list-providers`), and every session call then died
at encode; the operator burned a debugging session on what a pick-time warning would have
prevented.

Design sketch (attack before committing): the protocol already declares declines as data
in one place each (`models_shape() -> Option` is the precedent — the honest decline,
claude-code.md §7.2). A read surface — e.g. `bz --list-providers --json` gaining per-row
fields like `tools: bool` / `multi_turn: bool` derived from the protocol impl, never
stored — would let consumers (yog model_pick, lernie preflight) warn at selection time.
Keep it derived (single source of truth: the protocol's own reject arms), never a config
field; consider whether a closed capability enum or per-shape booleans is the narrower
interface. Do not add config.
