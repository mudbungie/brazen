Round 1, lane comparator. bz 0.0.14.

Goal: point a third-party agent harness at `bz --serve` so it runs on the box`s
ambient Claude credential (the `claude-session-direct` row, `credential:
ambient`).

First request through the ingress:

    {"error":{"code":401,"message":"no credential for this provider: set BRAZEN_API_KEY
     (or the provider API-key env var / --api-key) or run `bz --login --provider <id>`",
     "param":null,"type":"authentication_error"}}

The same model, same second, on the CLI:

    $ bz --provider claude-session-direct -m claude-haiku-4-5-20251001 --no-stream "Say OK"
    OK

Cause: `--serve` has no `--provider`, so the inbound `model` string is the only
routing input, and `claude-haiku-…` is owned by the built-in `anthropic` row
(api_key, no credential) rather than by the OAuth row that can actually answer.
specs/ingress.md §6 states this deliberately — "There is no new precedence rung
and no ingress-side model table" — and offers `model_aliases` as the recipe.

That recipe works, but only after an edit that is easy to get wrong and easy to
get *silently* wrong. What it took here:

    [[provider]]
    name = "claude-session-direct"
    model_prefixes = ["claude-"]                       # else `anthropic` owns the family
    model_aliases = { "gpt-4o" = "claude-sonnet-4-6" } # the harness`s hardcoded id
    …
    [ingress]
    listen = "127.0.0.1:PORT"

Two traps met on the way. (1) A user config may not DECLARE a second row with an
existing name to add a field — `bz` refuses the whole file with
`duplicate provider name "claude-session-direct"` — so the field has to be added
to the row already in the file, which means the recipe is "find and edit your
existing row", not "append this block". For a row that comes from the BUILT-IN
defaults there is no row in the file to edit, so the user must first reproduce
it. (2) `--serve` is a control op with `--provider` accepted on the command line
and silently irrelevant, so the obvious first attempt
(`bz --provider claude-session-direct --serve`) starts a server that ignores the
flag.

Proposed shape, smallest first: since `--provider` is already parsed and already
means "use this row", let `--serve` honour it as a **pin** — every inbound
request resolves to that row, the model string still substituting through its
aliases. That adds no config surface, no second routing table and no new
precedence rung (§6`s actual objection); it is the existing explicit signal,
applied at the one place it is currently dropped. Failing that, the refusal
above should at least name the row it routed to and why, since "no credential
for this provider" without the provider`s name is the one sentence that cannot
be acted on.

Filed p4: a comparator gap, not a defect — the documented recipe does work.
