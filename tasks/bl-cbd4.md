Operator ask 2026-09-22: 'add a gemini.google.com provider row' so a Google One / Gemini Pro account reaches Gemini (incl. image models) without a billed AI Studio key. FACTS (verified from google-gemini/gemini-cli source, packages/core/src/code_assist/{server,converter,oauth2,setup}.ts): gemini.google.com itself has no API; the sign-in route is the Code Assist backend https://cloudcode-pa.googleapis.com/v1internal — OAuth2 installed-app client (client_id 681255809395-oo8ft2oprdrnp9e3aqf6av3hmdib135j.apps.googleusercontent.com, PUBLIC client_secret GOCSPX-…, PKCE S256, loopback http://127.0.0.1:PORT/oauth2callback, scopes cloud-platform+userinfo.email+profile, access_type=offline, token endpoint https://oauth2.googleapis.com/token, a paste-the-code no-browser variant exists). Wire = the SAME GenerateContentRequest/Response, wrapped: POST /v1internal:streamGenerateContent?alt=sse with body {model, project, user_prompt_id?, request:<generateContent body>} (no model in the path) and each SSE chunk {response:<GenerateContentResponse>, traceId, …}. responseModalities passes through the CLI's converter. Prerequisite handshake: loadCodeAssist → cloudaicompanionProject (personal accounts; onboardUser FREE + LRO poll if no currentTier). DESIGN QUESTIONS: (1) protocol: a second google protocol id (google_code_assist) owning path+envelope+unwrap, reusing google_genai's body_map/chunk — or an envelope option on the existing id; (2) project id: an identity fact like the ChatGPT account_id (auth.md §10.4) — obtained at login, stored on the Cred, injected per request — but it lands in the BODY envelope not a header, and comes from an RPC not the id_token; alternative = operator-supplied row data (severable, no login mechanism) after a one-off discovery; (3) client_secret on an oauth2 row — does the row schema carry one (the ChatGPT/Anthropic rows are public clients without one)? (4) auth.md §7 'exactly one oauth2 row ships' budget → this row is a documented RECIPE, not a defaults.toml row (same ruling as Anthropic OAuth, bl-2485), unless the operator rules otherwise. FEASIBILITY GATE FIRST: a hand probe (scratchpad gca/probe.py) is capturing loadCodeAssist + streamGenerateContent with gemini-2.5-flash-image on the operator's account; if Code Assist refuses image models the row does not unblock image testing and the ball narrows to 'Google sign-in for text'.

---

PROBE RESULT 2026-09-22 (scratchpad gca/probe.py, operator signed in with the Gemini CLI installed-app client, PKCE, loopback; tokens obtained then shredded): loadCodeAssist 200 → allowedTiers=[standard-tier (enterprise, userDefinedCloudaicompanionProject=true, usesGcpTos)], ineligibleTiers=[free-tier, reasonCode UNSUPPORTED_CLIENT: 'This client is no longer supported for Gemini Code Assist for individuals. To continue using Gemini, please migrate to the Antigravity suite of products']; onboardUser FREE → 400 INVALID_ARGUMENT; streamGenerateContent (gemini-2.5-flash-image AND gemini-2.5-flash) → 403 PERMISSION_DENIED reason SUBSCRIPTION_REQUIRED (#3501). Google's deprecation page (developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals): 'Login with Google' for individuals incl. Google AI Pro/Ultra ended 2026-06-18; individuals are sent to Antigravity (closed client, no documented API/wire, unknown OAuth client); Standard/Enterprise (a GCP project with a Code Assist license) unaffected. gemini-cli issues #28229/#29279 confirm. CONCLUSION: a Google-sign-in row for an individual account has NO supported wire today; the only individual programmatic route is an AI Studio API key on a billed project, which the existing built-in google row already serves. Options for the operator: (a) enable billing on the AI Studio project → close this ball as won't-do; (b) a Code Assist Standard license (GCP project) → this design proceeds (client_secret row field + envelope protocol + project id as row DATA); (c) reverse-engineer Antigravity's client → not recommended (undocumented, ToS-adjacent, unstable).
