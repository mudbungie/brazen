## Finding

`bz --login --provider <row> --browser` is the only flow an oauth row without a `device` block can be fired in, and on a headless box it cannot complete:

- `browser_flow` (`src/auth/flows.rs`) binds the loopback, builds the authorize URL, then calls the launcher. `SystemBrowserLauncher::open` (`src/native.rs`) spawns `xdg-open`; where that program is absent the spawn errors and the login ends at once with *could not launch browser*.
- **The authorize URL is never printed.** The flow hands it to the launcher only, so a caller reading the two streams (a remote tool executor relaying them to a human elsewhere) has nothing to show.
- The redirect lands on the IPv4 loopback of the box running `bz` (`LoopbackReceiver`), so even a printed URL finishes only in a browser on that same box, or through a port-forward.

The case that matters: a box whose rows are served to a remote caller through `--envelope` (arch §5.10.5). The envelope's allowed set already carries `--login` and `--browser`, so the sign-in is reachable — and for a browser-only row it can never finish. The row then stays on a borrowed `ambient` credential, which brazen never refreshes and which lapses whenever the owning tool has not run for some hours.

## What is missing

A flow that completes with the human anywhere: print the authorize URL on stderr, and take the authorization code back without a local redirect. Two shapes, not decided here:

1. **A pasted-code flow as row data.** Where the vendor registers a redirect that displays the code instead of redirecting to loopback, the row names it; `bz` prints the URL, and the code arrives on a second command line (the PKCE verifier and state held in the store between the two, since an envelope run's stdin is fixed when it starts). Needs one more flag in the envelope's allowed set, and it must carry no credential — a one-use code bound to a verifier the caller never sees.
2. **Print the URL in the loopback flow and make a missing launcher non-fatal.** Smaller, and it fixes the silent case, but the redirect still lands on the far box's loopback, so it serves only an operator who forwards a port.

Unverified either way: which redirect URIs the vendor accepts for the client id a given row carries.

## Acceptance

A browser-only row on a box with no browser and no display is signed in by a caller that can only send command lines and read the two streams, and the stored credential refreshes on its own afterwards.
