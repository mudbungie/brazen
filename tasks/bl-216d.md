What to build: one control-plane mode flag (brazen names it). In that mode bz reads a single JSON object from standard input, {"args": [string...], "stdin": string (optional)}, validates args against a closed allow-set, then behaves exactly as `bz <args>` with `stdin` as its standard input: same stdout, same stderr, same exit code. The allow-set is the five command lines a yog server sends to a far machine: `--json --provider R` (a model call; stdin is the canonical request), `--list-providers --json`, `--login --json` (the sign-in catalog), `--list-models --provider R --json`, and `--login --provider R` with optional `--browser`. Everything else is refused with a usage error naming the flag, before anything runs: in particular any flag that names a file or a configuration, prints configuration, attaches input, changes the transport or starts the listener. Environment overrides are untouched: the environment is the executing box's own.

Why: yog docs/REMOTE.md section 5.7 (A provider call is an invocation). A foot advertises a tool named bz whose command is this mode; the tool contract delivers the tool input as JSON on stdin, so the input IS the command line. The allow-set lives here because only brazen knows which of its flags read files or print secrets, and nothing credential-shaped may cross the wire.

Tested by: for each allowed command line, the enveloped run's stdout, stderr and exit code are byte-identical to the direct run against the same mock provider (the model call included, streamed line by line, not buffered to the end); every flag outside the set is refused with exit 64 and nothing is spawned or read; a malformed envelope is a usage error. Spec first: the mode is added to the CLI spec before the code.

Order: independent of every other ball; thrall's example-document ball and yog's driven proof wait for the release that carries it.
